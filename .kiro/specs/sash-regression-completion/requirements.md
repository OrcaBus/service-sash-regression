# Requirements Document

## Introduction

The Sash Regression Service validates `sash` bioinformatics pipeline releases by comparing
outputs (VCFs, TSVs, Purple metrics, BCFtools stats) from a new version against a curated
baseline. This document captures the requirements for completing the production-ready state
of the service: the NotifierFunction, AggregatorFunction, PairComparatorFunction fan-out
architecture, comparison module refactor, infrastructure hardening, and security fixes.

## Glossary

- **PairComparatorFunction**: Lambda that processes exactly one tumor/normal pair comparison per
  invocation, downloads sash outputs, runs schema check and comparison, and emits a
  `SashRegressionPairCompleted` event.
- **AggregatorFunction**: Lambda that accumulates `SashRegressionPairCompleted` events for a
  given job and emits `SashRegressionComparisonCompleted` once all pairs have been received.
- **NotifierFunction**: Lambda that receives `SashRegressionComparisonCompleted` and posts a
  Slack message via Incoming Webhook.
- **WatcherFunction**: Existing Lambda that receives `WorkflowRunStateChange SUCCEEDED` events
  and fans out pair comparisons.
- **SubmitterFunction**: Existing Lambda that validates and submits new sash regression runs to
  OrcaBus.
- **JobId**: UUID generated by the Watcher per fan-out batch, correlating all pair events to one
  regression run.
- **Testdata_Config**: YAML file stored in S3 listing all tumor/normal pairs to compare.
- **OrcaBusMain**: The EventBridge event bus used by the OrcaBus platform.
- **Aggregator_State**: S3-backed JSON blob storing accumulated pair results for a given jobId.
- **Rollup**: The aggregated `SashRegressionComparisonCompleted` payload written to S3 and
  emitted to EventBridge after all pairs complete.
- **Schema_Check**: Validation that 9 required sash output files are present in a run directory.
- **Compact_Summary**: A structured dict summarising comparison outcome with status, criticalItems,
  and warningItems.
- **OverallStatus**: Aggregated worst-case status across all pairs: FAIL > MANUAL_CHECK > WARN > PASS.
- **PairIndex**: Zero-based index of a pair within a fan-out batch.

## Requirements

### Requirement 1: WatcherFunction Fan-Out

**User Story:** As an operator, I want the Watcher to fan out comparisons to one Lambda per pair
when a sash run succeeds, so that comparisons run in parallel and the Watcher does not time out
on large test suites.

#### Acceptance Criteria

1. WHEN the WatcherFunction receives a `WorkflowRunStateChange` event with `status: SUCCEEDED`
   and a `workflowRunName` matching the `umccr_tested_` prefix, THE WatcherFunction SHALL load
   the Testdata_Config from the S3 URI specified in `TESTDATA_CONFIG_S3_URI`.
2. WHEN the WatcherFunction loads the Testdata_Config, THE WatcherFunction SHALL generate a
   single UUID JobId for the fan-out batch.
3. WHEN the WatcherFunction fans out comparisons, THE WatcherFunction SHALL invoke the
   PairComparatorFunction asynchronously (`InvocationType="Event"`) once per pair in
   `config["pairs"]`.
4. WHEN invoking a PairComparatorFunction, THE WatcherFunction SHALL include `jobId`,
   `pairIndex` (0-based), `totalPairs`, `newVersion`, `baselineVersion`, `newOutputPath`,
   `baselineOutputPath`, `tumor`, `normal`, and `metadata` in the invocation payload.
5. THE WatcherFunction SHALL NOT invoke the PairComparatorFunction in a blocking sequential
   call that waits for completion — all invocations SHALL be fire-and-forget within the same
   handler execution.
6. WHEN the WatcherFunction receives a `WorkflowRunStateChange` event with `status: FAILED`,
   THE WatcherFunction SHALL log a warning and take no further action.
7. IF the `workflowRunName` does not match the `umccr_tested_sash_` pattern, THEN THE
   WatcherFunction SHALL return without invoking any Lambda.

### Requirement 2: PairComparatorFunction

**User Story:** As an operator, I want each pair comparison to run in an isolated Lambda
invocation, so that a failure in one pair does not block or corrupt the results of other pairs.

#### Acceptance Criteria

1. WHEN the PairComparatorFunction is invoked, THE PairComparatorFunction SHALL process exactly
   one tumor/normal pair per invocation using the `jobId`, `pairIndex`, `totalPairs`,
   `newOutputPath`, `baselineOutputPath`, `tumor`, `normal`, and `metadata` from the event.
2. WHEN the PairComparatorFunction completes a pair comparison, THE PairComparatorFunction SHALL
   emit a `SashRegressionPairCompleted` event to OrcaBusMain with source
   `sash-regression.pair-comparator`.
3. WHEN an unhandled exception occurs during pair comparison, THE PairComparatorFunction SHALL
   emit a `SashRegressionPairCompleted` event with `status: "FAIL"` and a `criticalItems` entry
   describing the error, and SHALL re-raise the exception to make the Lambda invocation fail
   visibly in CloudWatch.
4. THE PairComparatorFunction SHALL use a per-invocation temporary directory (via
   `tempfile.TemporaryDirectory`) for downloaded sash output files, ensuring cleanup on
   completion or error.
5. THE PairComparatorFunction SHALL upload per-pair result JSON to the S3 prefix
   `RESULT_S3_PREFIX/<new>-vs-<baseline>/<case>/<execId>/`.

### Requirement 3: Schema Check Gate

**User Story:** As an operator, I want the pair comparator to gate on schema validation before
running comparisons, so that incomplete sash outputs are reported as failures rather than
causing undefined parser behaviour.

#### Acceptance Criteria

1. WHEN the PairComparatorFunction downloads sash outputs, THE PairComparatorFunction SHALL run
   the Schema_Check on both the baseline and new run directories before invoking any comparison
   module.
2. IF the Schema_Check fails for either the baseline or the new run directory, THEN THE
   PairComparatorFunction SHALL set `status: "FAIL"`, add `"schema_check_failed"` to
   `criticalItems`, set `comparison` to `null`, and SHALL NOT invoke any comparison analysis
   module.
3. THE Schema_Check SHALL validate that all 9 required sash output files are present in the run
   directory.

### Requirement 4: Comparison Module Refactor

**User Story:** As a developer, I want the 3680-line monolithic comparison script split into
independently testable modules, so that I can unit-test individual parsers and the comparison
logic without running the full pipeline.

#### Acceptance Criteria

1. THE analysis module `app/comparator/analysis/runner.py` SHALL expose `run_pair_comparison(run1, run2, tumor, normal, output_dir)` which orchestrates all analysis steps and returns a Compact_Summary dict.
2. THE analysis module `app/comparator/analysis/vcf_parser.py` SHALL expose `vcf_analysis(vcf_path, tumor)` which streams all variants without a record cap, and SHALL log a WARNING (not truncate) when variant count exceeds 10 000.
3. THE analysis module `app/comparator/analysis/stats_parser.py` SHALL expose `parse_bcftools_stats(stats_path)` which parses BCFtools stats SN/TSTV/IDD sections and returns an empty dict (not raises) if expected sections are absent.
4. THE analysis module `app/comparator/analysis/base_dir.py` SHALL expose `get_base_dir(run_dir, tumor, normal)` which resolves the sash output subdirectory, supporting both single-underscore (`tumor_normal`) and double-underscore (`tumor__normal`) layouts, and SHALL raise `FileNotFoundError` if neither path exists.
5. WHEN `run_pair_comparison` is called, THE Runner SHALL call Python functions directly rather
   than spawning a subprocess to `comprehensive_sash_comparison.py`.
6. THE existing `comparison.py` SHALL be retained as a shim that delegates to `analysis.runner`,
   preserving backward compatibility for any direct-invoke SOP workflows.

### Requirement 5: AggregatorFunction

**User Story:** As an operator, I want a dedicated Lambda to accumulate pair results and produce
a rollup summary when all pairs complete, so that I can get a single PASS/FAIL verdict across
all test cases.

#### Acceptance Criteria

1. WHEN the AggregatorFunction receives a `SashRegressionPairCompleted` event, THE
   AggregatorFunction SHALL load the Aggregator_State from S3 for the given `jobId`, or create
   a new state if none exists.
2. WHEN the AggregatorFunction appends a pair result, THE AggregatorFunction SHALL be idempotent
   on duplicate `pairIndex` values — a pair with the same `pairIndex` received more than once
   SHALL be counted only once, and `receivedPairs` SHALL equal the cardinality of distinct
   `pairIndex` values seen.
3. THE AggregatorFunction SHALL write Aggregator_State back to S3 using a conditional put
   (object versioning + CAS) to prevent lost-update race conditions when two pair events arrive
   simultaneously.
4. IF the conditional write fails with HTTP 412 (PreconditionFailed), THEN THE
   AggregatorFunction SHALL retry the read-modify-write up to 3 times before raising an
   exception.
5. WHEN `receivedPairs == totalPairs`, THE AggregatorFunction SHALL compute the Rollup,
   upload it to
   `s3://umccr-research-dev/sash-regression/<new>-vs-<baseline>/jobs/<jobId>/rollup.json`,
   and emit a `SashRegressionComparisonCompleted` event to OrcaBusMain with source
   `sash-regression.aggregator`.
6. THE AggregatorFunction SHALL NOT emit a `SashRegressionComparisonCompleted` event when fewer
   than `totalPairs` distinct pair events have been received.

### Requirement 6: Status Rollup

**User Story:** As an operator, I want the aggregated status to reflect the worst outcome across
all pairs, so that any failure is surfaced prominently and not masked by passing pairs.

#### Acceptance Criteria

1. WHEN computing the OverallStatus, THE AggregatorFunction SHALL set `overallStatus` to `FAIL`
   if any pair has `status: "FAIL"`.
2. WHEN no pair has `status: "FAIL"` but at least one pair has `status: "MANUAL_CHECK"`, THE
   AggregatorFunction SHALL set `overallStatus` to `MANUAL_CHECK`.
3. WHEN no pair has `status: "FAIL"` or `status: "MANUAL_CHECK"` but at least one pair has
   `status: "WARN"`, THE AggregatorFunction SHALL set `overallStatus` to `WARN`.
4. WHEN all pairs have `status: "PASS"`, THE AggregatorFunction SHALL set `overallStatus` to
   `PASS`.
5. THE AggregatorFunction SHALL truncate `criticalItems` in the Rollup to a maximum of 8 entries
   aggregated across all pairs.

---

### Requirement 7: NotifierFunction

**User Story:** As an operator, I want a Slack notification when a regression comparison
completes, so that I know immediately whether the new sash version passes or fails its tests.

#### Acceptance Criteria

1. WHEN the NotifierFunction receives a `SashRegressionComparisonCompleted` event, THE
   NotifierFunction SHALL retrieve the Slack Incoming Webhook URL from AWS Secrets Manager using
   the secret ID specified in `SLACK_WEBHOOK_SECRET_ID`.
2. WHEN the NotifierFunction formats the Slack message, THE NotifierFunction SHALL use Slack
   Block Kit format with a header block containing the status emoji and version comparison
   (`<emoji> Sash Regression: <newVersion> vs <baselineVersion>`).
3. THE NotifierFunction SHALL map status values to emoji as follows: `PASS` → ✅, `WARN` → ⚠️,
   `FAIL` → ❌, `MANUAL_CHECK` → 🔍.
4. THE NotifierFunction SHALL include a section block with overall status, pairs passed count,
   and failures count.
5. WHEN the Rollup contains `criticalItems`, THE NotifierFunction SHALL include the first 5
   critical items in the Slack message.
6. THE NotifierFunction SHALL include a link to the rollup results in S3 (as an S3 console URL
   derived from `rollupS3Uri`).
7. WHEN the Slack webhook POST returns a non-2xx HTTP status, THE NotifierFunction SHALL raise
   a `RuntimeError`, causing the Lambda to fail and trigger EventBridge's at-least-once retry.

### Requirement 8: SubmitterFunction Hardening

**User Story:** As a developer, I want the Submitter to handle token expiry, WRU error responses,
and portal run ID entropy correctly, so that the submission path is robust under all conditions.

#### Acceptance Criteria

1. WHEN `_orcabus_token()` is called and the cached token was fetched more than
   `_TOKEN_TTL_SECONDS` (600 s) ago, THE SubmitterFunction SHALL fetch a fresh token from
   Secrets Manager and update the cache.
2. WHEN `_orcabus_token()` is called and the cached token was fetched within
   `_TOKEN_TTL_SECONDS`, THE SubmitterFunction SHALL return the cached token without calling
   Secrets Manager.
3. WHEN the WruDraftValidator Lambda invocation returns a `FunctionError` response, THE
   SubmitterFunction SHALL raise a `RuntimeError` containing the raw error payload.
4. WHEN the WruDraftValidator Lambda returns an HTTP `statusCode` other than 200, THE
   SubmitterFunction SHALL raise a `RuntimeError`.
5. WHEN the WruDraftValidator Lambda returns HTTP 200 but the response body contains a non-null
   `error` field, THE SubmitterFunction SHALL raise a `RuntimeError`.
6. THE SubmitterFunction SHALL generate portal run IDs using `secrets.token_hex(4)` (not
   `random.choices`) to use a cryptographically secure PRNG.

### Requirement 9: S3 Path Traversal Prevention

**User Story:** As a security engineer, I want the S3 download utility to reject keys that would
escape the local download directory, so that a malicious or malformed S3 key cannot overwrite
arbitrary filesystem paths inside the Lambda container.

#### Acceptance Criteria

1. WHEN `download_s3_dir()` processes an S3 object key, THE S3_Utility SHALL resolve the
   destination path using `Path.resolve()` and validate it with `Path.is_relative_to(local_dir)`
   before writing any file.
2. IF an S3 object key resolves to a path outside `local_dir`, THEN THE S3_Utility SHALL raise
   a `ValueError` and SHALL NOT write any data to disk for that key.
3. THE S3_Utility SHALL use a module-level cached `boto3` S3 client to avoid per-call credential
   resolution overhead.

### Requirement 10: CDK Infrastructure

**User Story:** As a developer, I want the CDK stack to declare all five Lambda functions with
correct IAM roles and EventBridge rules, so that the service is fully deployable without manual
resource creation.

#### Acceptance Criteria

1. THE DeploymentStack SHALL define five Lambda functions: SubmitterFunction, WatcherFunction,
   PairComparatorFunction, AggregatorFunction, and NotifierFunction, each with its own dedicated
   IAM role.
2. THE DeploymentStack SHALL define three EventBridge rules on OrcaBusMain:
   - A rule triggering WatcherFunction on `WorkflowRunStateChange` events with `workflowRunName`
     prefix `umccr_tested_`.
   - A rule triggering AggregatorFunction on `SashRegressionPairCompleted` events from source
     `sash-regression.pair-comparator`.
   - A rule triggering NotifierFunction on `SashRegressionComparisonCompleted` events from
     source `sash-regression.aggregator`.
3. THE WatcherRole SHALL grant `lambda:InvokeFunction` on PairComparatorFunction and
   `s3:GetObject`/`s3:ListBucket` on the results bucket for config reads.
4. THE PairComparatorRole SHALL grant `events:PutEvents` on OrcaBusMain.
5. THE AggregatorRole SHALL grant `s3:GetObject`, `s3:PutObject`, and `s3:ListBucket` on the
   results bucket, and `events:PutEvents` on OrcaBusMain.
6. THE NotifierRole SHALL grant `secretsmanager:GetSecretValue` scoped to the Slack webhook
   secret ARN pattern `sash-regression/slack-webhook*`.
7. THE DeploymentStack SHALL supply environment variables `PAIR_COMPARATOR_FUNCTION_NAME` and
   `TESTDATA_CONFIG_S3_URI` to the WatcherFunction.
8. THE DeploymentStack SHALL supply environment variables `EVENTS_BUS_NAME`, `RESULTS_BUCKET`,
   and `RESULT_S3_PREFIX` to the AggregatorFunction.
9. THE DeploymentStack SHALL supply environment variable `SLACK_WEBHOOK_SECRET_ID` to the
   NotifierFunction.

### Requirement 11: Per-Stage Constants

**User Story:** As a developer, I want per-stage constants for the WRU validator function name
and Slack webhook secret ID, so that each environment (beta, gamma, prod) uses its own
isolated resources.

#### Acceptance Criteria

1. THE `getStageConstants()` function in `infrastructure/stage/constants.ts` SHALL return a
   `slackWebhookSecretId` field with stage-specific values:
   `sash-regression/slack-webhook-beta` (BETA), `sash-regression/slack-webhook-gamma`
   (GAMMA), and `sash-regression/slack-webhook` (PROD).
2. THE `WRU_VALIDATOR_FUNCTION_NAME` map in `infrastructure/stage/constants.ts` SHALL contain
   distinct values for BETA, GAMMA, and PROD stages rather than the same value for all stages.

### Requirement 12: Repository Hygiene

**User Story:** As a developer, I want `cdk.out/` excluded from git, so that stale synthesis
artifacts and full application source copies are not committed to the repository.

#### Acceptance Criteria

1. THE `.gitignore` file SHALL include an entry for `cdk.out/` to prevent CDK synthesis
   artifacts from being committed.
2. THE existing `cdk.out/` directory and its contents SHALL be removed from git tracking via
   `git rm -r --cached cdk.out/`.

### Requirement 13: Unit Tests

**User Story:** As a developer, I want unit tests for all new and modified modules, so that I
can verify correctness without running the full AWS integration.

#### Acceptance Criteria

1. THE test suite SHALL include `test_aggregate.py` covering: `append_pair()` idempotency on
   duplicate `pairIndex`, `build_rollup()` status precedence (FAIL > MANUAL_CHECK > WARN >
   PASS), and conditional write conflict retry logic.
2. THE test suite SHALL include `test_notify.py` covering: `format_slack_message()` for each
   of the four status values (PASS, WARN, FAIL, MANUAL_CHECK), and `post_slack_message()`
   raising `RuntimeError` on non-2xx response.
3. THE test suite SHALL include `test_analysis_base_dir.py` covering: single-underscore path
   found, double-underscore path found, and neither path existing (raises `FileNotFoundError`).
4. THE test suite SHALL include `test_analysis_vcf_parser.py` covering: correct variant count
   with a synthetic VCF fixture, and a WARNING log when variant count exceeds 10 000.
5. THE test suite SHALL include `test_analysis_stats_parser.py` covering: correct parsing of
   BCFtools SN/TSTV sections, and returning an empty dict when sections are absent.
6. THE test suite SHALL extend `test_s3_utils.py` to cover: a path traversal attack key
   (`../../etc/passwd`) raising `ValueError`.
7. THE test suite SHALL extend `test_submit.py` to cover: token TTL (second call within TTL
   skips Secrets Manager; expired call re-fetches), and all three WRU error modes raising
   `RuntimeError`.
8. THE test suite SHALL extend `test_watcher_handler.py` to cover: N pairs producing N
   `PairComparatorFunction` async Lambda invocations with correct `pairIndex` and `totalPairs`.
9. WHEN all unit tests are executed, THE test suite SHALL pass with no failures.
